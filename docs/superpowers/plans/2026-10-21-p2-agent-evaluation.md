# P2 Agent 端到端评测实施计划

## 边界与设计判断

- 唯一工作目录为本仓库；保留现存 `docker-compose.yml`、`.dockerignore`、`.serena/` 未提交状态。
- 只加入独立评测数据、脚本、测试和报告。默认不动 Agent 核心实现；仅在发现阻断/错误写入的可复现缺陷后做最小修复。
- 40 条是固定用例集目标，不预先等同于 40 条已实测成功。真实模型、Mock、未执行分别标注。
- 每个 case 独立计入分母；不因超时、错误、不可判定而从“已尝试”分母移除。未执行单列，不计算成功率。
- 只用合成身份与订单。写操作用 P2 专属唯一订单，先确认全局未占用。不得清库或接真实支付。
- 中转站计费未知；先用少量真实 HTTP case 试跑，用户确认费用上限前不跑全量 40 条。
- 不声明 Hybrid 性能：OpenSearch 关闭时单独报告 Dense 实测结果。回答忠实性没有人工判读时标为未评。
- 用户已给出完整专家方案并明确要求“综合评估和执行”，将其视为设计范围批准。由于单仓库约束和已有未提交修改，不创建工作树；由于本轮没有授权子代理，采用本地自检和完整测试。

## A. 基线和字段核对

1. 记录 Git HEAD/status、六服务状态与健康接口。只读读取 P0/P1 报告、现有评测、API schema、数据库模型、配置状态，不读取或输出 `.env` 密钥。
2. 确认聊天、确认、运行轨迹和只读 DB 计数路径。说明模型每个案例可能多次调用及成本未知。
3. 输出 A 阶段进展和限制。

## B. 固定用例

1. 新建 `evals/agent_cases.jsonl`，按知识 8、订单 8、多轮 6、HIL 8、隔离 4、异常 6 分组。
2. 每例定义输入步骤、合成身份、前置数据、期望 HTTP/图状态、工具/参数、DB 变化、自动判据；无法自动判读的语义项显式标记人工复核。
3. 写入场景的 seed 在执行前全局查重，拒绝复用已有订单，不更新旧单。
4. 测试 JSONL schema、ID 唯一性、分组数量和高风险场景的安全门槛。

## C. 独立执行器（TDD）

1. 先写 Mock HTTP/DB 单测，覆盖选择器、成功与失败计数、超时、脱敏、写入前后计数、重复确认 409、报告导出。
2. 新建 `scripts/evaluate_agent.py`：`--case-id`/`--category`/`--max-cases`、明确的 `--live` 开关、请求超时及硬调用数上限、串行执行；默认只验证数据，不调用外部 API。
3. 原始结果 JSON 保存 case 状态、HTTP 状态、简化 trace/工具名/来源、run/thread/confirmation ID、每请求 latency、DB 前后值及失败类型；禁止持久化凭据、完整 Prompt、自由文本敏感响应。
4. 生成 Markdown 汇总，记录 Git SHA、时间、种子、模型和可公开的配置；做样本量和分母检查。
5. Mock 运行后选少量无写入真实案例试跑；再根据预算决定扩展。

## D. Dense RAG 专项

1. 新建清洗后的固定标注，区分当前有效/过期/实时/无依据；仅有效知识进入 Hit@1/3/5、MRR 分母，其余测路由/安全处理。
2. 复用 `RagService.retrieve` 和现有容器环境，逐题保存来源 rank；报告与旧 0.65/0.60 不可横比。
3. 回答忠实性未人工复核不报自动成功；若实测回答，只保留出处与人工待检标记，不调用额外 LLM 裁判。

## E. 延迟与稳定性

1. 仅使用真实 HTTP 请求的单次端到端耗时，按请求与按案例分列，串行执行；计算 P50/P95/mean、样本量、失败类型。
2. 小样本 P95 明确不代表生产 SLA；SSE 首包不称 TTFT，API 延迟不称 TPOT。

## F. 失败分析与交付

1. 将每项已尝试失败归入固定分类，并核对 Trace、状态及 DB 证据；若存在安全/写入缺陷，先复现、补测试、再做最小修复。
2. 运行完整现有+新增测试、Ruff 关键规则、差异与敏感内容扫描。
3. 提交总体、RAG、延迟报告及机器可读结果。只按明确文件暂存；不推送。P2 后停止。

## 可执行验收

- `python scripts/evaluate_agent.py --validate` 不需要模型/数据库即可校验 40 例。
- Mock 单测证明成功、失败、跳过/未执行的分母与脱敏正确。
- 真实 HTTP 试跑输出实际 run/trace/latency；无证据不标 PASS。
- Dense 检索报告给出逐题 rank、Hit@1/3/5、MRR 和错误案例。
- 报告明确原项目能力、本轮新增、开放风险与 P3 是否具备前提。
