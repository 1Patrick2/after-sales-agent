# P3 本地运行与 5 分钟演示

仅面向本仓库的**合成数据、本地服务**。本文件提供操作顺序，不保证从空磁盘一次性部署成功；P0/P1/P2.1 的真实证据链接在文末。退款指创建售后**申请工单**，不触发支付系统。

## 前提与配置边界

- WSL Ubuntu-22.04、Docker Compose、现有 Python 3.11 app 镜像、MySQL/Redis/Qdrant/PostgreSQL/Ollama 本地服务；模型使用有效 OpenAI-compatible 聊天 API。不要把 `.env`、Bearer/JWT 或连接密码贴进演示、Issue 或截图。
- `.env` 已存在时**不要覆盖**。必要键：`LLM_API_KEY`、`LLM_BASE_URL`、`LLM_MODEL`；`EMBEDDING_PROVIDER=ollama`、`EMBEDDING_BASE_URL`、`EMBEDDING_MODEL`、`EMBEDDING_DIMENSION=512`；`GRAPH_CHECKPOINTER=postgres`、对应 PostgreSQL URL；Qdrant URL。当前验证模型是 `gpt-5.6-terra` 与 `qllama/bge-small-zh-v1.5:q8_0`。改变 Embedding 或维度需要核对并重建对应向量集合，不能直接复用旧 512 维索引。
- 本地常驻 `SECURITY_ENABLED=false`、`MCP_AFTER_SALES_ENABLED=false`、`OPENSEARCH_ENABLED=false`。这意味着仅能在可信本机演示，绝不能对外开放端口。独立 JWT 测试不等于常驻服务开启鉴权。
- **部署配置不是纯 Git 快照**：当前 `docker-compose.yml` 含用户未提交的 localhost 绑定、Ollama/Profile 和 MCP 依赖调整；`.dockerignore` 也未跟踪。保留这些内容，不在 P3 擅自提交或覆盖。`docker-compose.p0.yml` 为已跟踪的源码只读挂载层，可让旧镜像加载当前代码。全新镜像构建、全新数据库迁移/入库的组合尚未端到端验证。
- Compose 的本地默认数据库密码和 `.env.example` 占位配置仅供演示，**不是生产安全配置**。`/health/ready` 只核对必填设置，不能替代数据库、Qdrant 或模型调用验证。

## 现有环境启动与轻量检查

以下命令在仓库目录的 WSL Shell 中执行；仅适用于镜像、卷、数据库与模型已有的机器：

```bash
docker compose --profile durable --profile embedding up -d mysql redis qdrant checkpoint-postgres ollama
docker compose -f docker-compose.yml -f docker-compose.p0.yml up -d --no-deps --no-build app
docker compose --profile durable --profile embedding ps
curl -fsS http://127.0.0.1:8000/health/live
curl -fsS http://127.0.0.1:8000/health/ready
```

若镜像/模型尚未下载，上述 `--no-build` 路径不能代替构建；可先按 `Dockerfile`、`requirements.txt`、`alembic.ini` 和 `scripts/ingest_docs.py` 准备环境，但这条**干净重建路径当前未验收**，不要在正式演示前首次尝试。已有模型在容器中的存在性可用 `docker compose --profile embedding exec -T ollama ollama list` 检查；缺失时再决定是否下载，避免临场等待大镜像。不要运行会更新已有样例订单的 `scripts/seed_sample_data.py`。

默认回归是现有测试而非 40 条付费模型请求。当前镜像须挂载仓库测试与评测文件：

```bash
docker compose -f docker-compose.yml -f docker-compose.p0.yml run --rm --no-deps -T \
  -e P0_DB_TEST=1 -v "$PWD/tests:/app/tests:ro" -v "$PWD/evals:/app/evals:ro" \
  -v "$PWD/reports:/app/reports:ro" -v "$PWD/pyproject.toml:/app/pyproject.toml:ro" \
  app python -m pytest -q /app/tests
```

其中 3 个跳过项为有意隔离的外部依赖测试；它们的独立实测证据见 P1/P2.1 报告。`pytest` 不等同于真实 LLM 端到端成功率。

## 演示数据：只新增两条全新合成订单

在**确认是本地演示 MySQL** 后，为拒绝与批准各选一个全局未占用的 8–24 位数字订单号。下面的 `<REJECT_ORDER_ID>`、`<APPROVE_ORDER_ID>` 都是占位符，先替换。此脚本先检查两号未占用才插入，不更新旧订单；不要复用 P0/P2 中已批准的订单。

```bash
docker compose -f docker-compose.yml -f docker-compose.p0.yml exec -T app \
  python scripts/seed_refund_acceptance_data.py <REJECT_ORDER_ID> <APPROVE_ORDER_ID>
```

脚本写入 `tenant_id=default`、`user_id=p0_acceptance` 的模拟已发货订单。若不想增加任何数据，可**只展示** [P0 验收报告](p0_refund_hil_acceptance_2026-10-21.md)和 [P2.1 DB 对照](p2_1_agent_optimization_2026-10-22.md)，不要再对已批准订单重复发起新业务申请。

## 场景一：订单只读查询（约 45 秒）

将 `<REJECT_ORDER_ID>` 替换为刚插入的订单号：

```bash
curl -sS -X POST http://127.0.0.1:8000/api/v1/chat \
  -H 'Content-Type: application/json' \
  -d '{"tenant_id":"default","user_id":"p0_acceptance","question":"查订单<REJECT_ORDER_ID>的状态和物流。"}'
```

预期：HTTP 200，答复包含真实模拟订单状态，`tool_calls/tool_results` 可见 `query_order_status` 或相应只读工具；模型存在波动，实际工具以 Trace 为准，不只凭自然语言下结论。记录响应中的 `conversation_id`、`thread_id`、`run_id`。源码：`routes_chat.chat → CustomerServiceAgent.answer → Graph rewrite/retrieve/decide → ToolRegistry.execute → BusinessGateway.query_order_status`。只读证据：[P2 最终 Trace](p2_trace_evidence.json)与 [P2.1 网络结果](p2_1_final_network_2026-10-22.json)。

## 场景二：多轮指代与知识咨询（约 45 秒）

复用上一轮返回的**两个 ID**，而不只是 `conversation_id`：

```bash
curl -sS -X POST http://127.0.0.1:8000/api/v1/chat \
  -H 'Content-Type: application/json' \
  -d '{"tenant_id":"default","user_id":"p0_acceptance","conversation_id":"<CONVERSATION_ID>","thread_id":"<THREAD_ID>","question":"这个订单的单号是多少？"}'
```

然后可换新会话问 `七天无理由退货的条件是什么？`；答案需要核对 `knowledge[].source` 与政策原文，不能只看是否“像是正确答案”。源码：`QuestionRewriteService.resolve`、`QuestionRouter.route`、`RagService.retrieve`、Graph `retrieve/evaluate_retrieval/finalize`。证据：[P2.1 最终报告的 C03/K01–K08](p2_1_agent_optimization_2026-10-22.md)。K01 在最终运行命中了政策但漏掉明确 7 天，正好用于说明“检索命中 ≠ 回答完整”。

## 场景三：退款申请的拒绝与批准（约 2 分钟）

分别用**独立**模拟订单发起明确提交，并给出理由：

```bash
curl -sS -X POST http://127.0.0.1:8000/api/v1/chat \
  -H 'Content-Type: application/json' \
  -d '{"tenant_id":"default","user_id":"p0_acceptance","question":"请为订单<REJECT_ORDER_ID>提交退款申请，原因是耳机持续杂音。"}'
```

期待 `status=waiting_confirmation`、`pending_confirmation.id` 与原 `thread_id`；此时先用下述只读命令核对 `refund_ticket_count=0`。若模型要求补充信息（例如退款原因、签收状态），这是可接受的安全澄清，不应凭空编造参数或越过确认；补齐真实合成上下文后再继续。

```bash
docker compose -f docker-compose.yml -f docker-compose.p0.yml exec -T app \
  python scripts/verify_p1_refund.py default p0_acceptance <REJECT_ORDER_ID>
curl -sS 'http://127.0.0.1:8000/api/v1/confirmations/<CONFIRMATION_ID>?tenant_id=default&user_id=p0_acceptance'
curl -sS http://127.0.0.1:8000/api/v1/graph/threads/<THREAD_ID>
```

图应在 `await_confirmation` 挂起，确认单为 `pending`。拒绝分支：

```bash
curl -sS -X POST http://127.0.0.1:8000/api/v1/confirmations/<CONFIRMATION_ID>/reject \
  -H 'Content-Type: application/json' \
  -d '{"tenant_id":"default","user_id":"p0_acceptance","reason":"演示拒绝"}'
```

再次只读查询订单，预期确认单 `rejected`、退款申请工单仍 0。批准分支使用**另一条** `<APPROVE_ORDER_ID>`，重复“提交申请→确认前 DB 0”步骤，然后：

```bash
curl -sS -X POST http://127.0.0.1:8000/api/v1/confirmations/<APPROVE_CONFIRMATION_ID>/approve \
  -H 'Content-Type: application/json' \
  -d '{"tenant_id":"default","user_id":"p0_acceptance"}'
docker compose -f docker-compose.yml -f docker-compose.p0.yml exec -T app \
  python scripts/verify_p1_refund.py default p0_acceptance <APPROVE_ORDER_ID>
```

期待确认单 `executed`、MySQL 工单 **0→1**，且只是 `category=refund` 的 `open` 售后申请工单。再次对**同一确认 ID**批准应返回 409，DB 仍 1；不要对已批准订单创建**新的确认 ID** 来冒充幂等验证。源码：`nodes.create_pending_action/await_confirmation`、`CustomerServiceGraphRuntime.resume`、`CustomerServiceAgent._resume_confirmation_unlocked`、`nodes.apply_confirmation`、`ConfirmationService.approve/reject`、`BusinessGateway.create_refund_case`。跨重启恢复的实测证据在 [P0 报告](p0_refund_hil_acceptance_2026-10-21.md)，演示时无需再次重启服务。

`run_id` 可查 `GET /api/v1/agent-runs/<RUN_ID>`；`thread_id` 可查 Graph 快照。上述运维接口在隔离开启鉴权时要求 operator/admin 且按持久化运行归属校验；本地默认未启用鉴权，仅可信机器内查看。源码：`routes_agent_runs.get_agent_run`、`routes_graph.get_graph_thread`。
